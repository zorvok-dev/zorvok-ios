The CocoaPods-compatible dependency manager for iOS. Publish pods in one command.

Zero Overhead, Reliable Versions, One Kit

Zorvok runs on top of CocoaPods: same Podfile, same pod install results. It adds one-command publishing to a free public registry, which keeps working after CocoaPods trunk goes read-only.

CocoaPods trunk becomes read-only on December 2, 2026. Existing pods keep installing, but trunk stops accepting new pods and new versions (CocoaPods' Trunk Read-only Plan). Zorvok gives those new versions a place to go, without changing how your app installs its pods.

Why teams use Zorvok

It keeps CocoaPods, keeps your Podfile, and fills the gaps CocoaPods leaves.

Drop-in for pod install

Same Podfile, same Pods/, byte-identical Podfile.lock. You can go back to pod install at any time.

One-command publishing

zorvok trunk push publishes like pod trunk push did, and the registry accepts it automatically, usually within a minute.

Source and binary pods

Publish from a git tag or from a zipped xcframework: only the podspec goes to the registry, your code stays where its source points.

Private and public pods together

Add a company registry without editing your Podfile. If a pod could come from two sources, Zorvok refuses to guess.

Every pod command

zorvok update, outdated, lib lint, spec, deintegrate and the rest map one-to-one.

Free and open source

MIT licensed. The public registry is a GitHub repository: no server, no fees.

Why you can trust it with your build

Everything below is in the open source and its tests. Check it yourself rather than taking our word for it.

It's CocoaPods doing the work

zorvok install runs the real pod install. Resolution, Podfile.lock and Xcode integration are CocoaPods' own code, and tests check the lockfile comes out byte-identical.

No lock-in, ever

Zorvok writes nothing CocoaPods doesn't understand. Stop using it tomorrow and pod install carries on exactly as before.

Pods stay with their owners

A pod already on CocoaPods trunk can only be published here by its owners there, matched against trunk's own records, never against anything the publisher submits.

No silent source picks

If a pod could come from two registries, Zorvok stops and asks you to pin it, which closes the door on dependency-confusion attacks.

The registry never runs your code

Its publish check reads podspecs as data. It runs nothing from a pull request, and published versions can never be changed or deleted.

A security review, in the open

Quick start

You need a Mac with Xcode and CocoaPods. Zorvok works with the project you already have.

# one command: adds the tap and trusts only this formula
brew install zorvok-dev/tap/zorvok
zorvok doctor              # checks Ruby, CocoaPods and git
cd ~/Projects/MyApp        # any project with a Podfile
zorvok install             # runs pod install underneath

Open your .xcworkspace as usual. Update Zorvok later with brew upgrade zorvok.

Publish a pod after CocoaPods trunk goes read-only

Only the podspec goes to the registry; your code, frameworks and xcframeworks stay wherever its source points.

gh auth login       # once: publishing uses your GitHub account
cd ~/Projects/MyPod
zorvok trunk push

Your users add one line to get it:

pod 'MyPod', '~> 2.1', :source =>
  'https://raw.githubusercontent.com/zorvok-dev/zorvok-specs/main/'
  1. Lint and convert. trunk push checks your podspec and converts it to JSON.
  2. Pull request. It opens one for you, from your fork of the public registry.
  3. Automatic check. The version must be new, you must own the pod, a pod already on CocoaPods trunk can only come from its trunk owners, and prepare_command isn't allowed.
  4. Published. Merged and indexed automatically, usually within a minute. If a check fails, trunk push says exactly why.

Frequently asked questions

Is Zorvok a replacement for CocoaPods?

No. Zorvok runs CocoaPods underneath: zorvok install calls the real pod install, so dependency resolution, Podfile.lock and Xcode integration are CocoaPods' own. Zorvok adds registries, publishing and safety checks on top.

What happens to my app when CocoaPods trunk goes read-only?

Existing pods keep installing; the CocoaPods maintainers' plan keeps existing builds working. What stops on December 2, 2026 is publishing new pods and new versions to trunk. Zorvok gives those new versions a place to go.

How do I keep publishing a pod that's already on CocoaPods trunk?

Run zorvok trunk push in the pod's repository. Because the name exists on trunk, you need to be one of its owners there, which Zorvok checks automatically. Users then add :source => 'https://raw.githubusercontent.com/zorvok-dev/zorvok-specs/main/' to that pod's line in their Podfile.

Do I have to change my Podfile to use Zorvok?

No. zorvok install works with your existing Podfile. To get a pod from Zorvok's registry, either pin it with one :source on its line or use zorvok install --native with the registry configured.

Can I go back to pod install?

Yes, at any time. Zorvok writes nothing CocoaPods doesn't understand.

Is Zorvok free?

Yes. Zorvok is open source under the MIT license, and publishing to its public registry is free; it needs only a GitHub account.

What does Zorvok stand for?

ZORVOK is short for Zero Overhead, Reliable Versions, One Kit: no new Podfile format or workflow to learn, versions that never change once published, and one tool for installing and publishing pods.

Project status, and who's behind it

Where Zorvok is today

Zorvok is young, and we'd rather say so than surprise you:
