# ADR 0010: `trunk push` publishes to the public registry, and the registry merges it itself

## Status
Accepted

## Context
After ADR 0009, `zorvok trunk push` only published to a live `zorvok-registry-ios` server, which nobody runs publicly. The free public registry, `zorvok-specs`, could only be published to by hand: convert the podspec with `pod ipc spec`, fork the repository, add `Specs/<name>/<version>/<name>.podspec.json` (plus `OWNERS` for a new pod), open a pull request, and wait for a maintainer to merge it.

That's far from what CocoaPods users expect. With CocoaPods, a pod's code, frameworks and xcframeworks stay wherever its podspec's `source` points; only the podspec goes to the registry, and `pod trunk push` puts it there in one command. trunk.cocoapods.org can do that because it's a server holding write access to the Specs repo: it checks the session, checks ownership in its database, and commits the podspec as a bot. CocoaPods trunk also becomes read-only on December 2, 2026, so "keep publishing new versions of an existing pod" is exactly what pod authors will come to Zorvok for.

The public registry deliberately has no server (ADR 0009), so something else has to hold write access and make that decision.

## Decision
GitHub plays trunk.cocoapods.org's part:

- **Identity is the publisher's GitHub account**, in place of trunk's email session: `gh auth login` once (or `GH_TOKEN`/`GITHUB_TOKEN`), the way `pod trunk register` is a one-time step. OWNERS files already list GitHub usernames (ADR 0009).
- **`zorvok trunk push` makes the pull request itself** (`internal/publicregistry`). It lints and converts the podspec exactly as before (`publisher.Prepare`), then checks the registry first: the version must be new, and an existing pod's OWNERS must list the publisher. It forks the registry if needed, commits the JSON (plus an OWNERS file listing the publisher, for a brand-new pod) as one commit on top of the registry's tip, moves a branch to it in one step, and opens the pull request, or reuses the one an earlier attempt opened. One commit and one branch move mean the registry's workflow runs once, on the finished change, and the branch never points at a commit the registry already has, which GitHub can treat as the pull request having been merged.
- **The registry merges valid publishes itself** (`zorvok-specs/.github/workflows/publish.yml`, on `pull_request_target`). It runs `validate-pr.sh` (immutability, structure, ownership; unchanged) and a new `publish-policy.sh` (is this a change a machine should merge on its own?). It merges with `--match-head-commit`, so exactly the judged commit lands, regenerates the index in the same job, and comments a verdict whose first line is machine-readable: `<!-- zorvok-publish sha=<commit> verdict=published|needs-review|rejected -->`.
- **`trunk push` waits for that verdict** — on its own commit, posted by `github-actions[bot]`, nothing else counts — and reports it the way `pod trunk push` would: `Published MyPod 1.0.0`, or why not.
- **Routing**: with no `registry_url`, or with `registry_url` set to any of the public registry's addresses, `trunk push` publishes there. A `registry_url` naming anything else is a registry server, published to as before, with `zorvok login`.

What still needed a person (`publish-policy.sh`), so the automation couldn't be turned against anyone — **superseded by the amendment below, which removes the person entirely**:

- **A name that's already on CocoaPods trunk**, on its first Zorvok publish. Otherwise anyone could claim `Alamofire` here first. A maintainer confirms it once; that pod's later versions publish automatically, held to its OWNERS. Trunk is checked through the same sharded index files CocoaPods' own CDN source reads.
- **Anything other than adding podspecs** (plus a new pod's OWNERS): an OWNERS edit, a change to the registry's scripts or workflows, an OWNERS file with no version.
- **`prepare_command`**, which runs shell commands on every machine that installs the pod; CocoaPods trunk stopped accepting new podspecs that use it in May 2025.

## Consequences
- Publishing to the public registry is one command after a one-time `gh auth login`, and it usually finishes in about a minute.
- `trunk push` with no `registry_url` no longer targets the local development server (`http://localhost:8080`); developing against a local `zorvok-registry` now needs `registry_url` set explicitly. Every other registry command still falls back to that default.
- `pull_request_target` runs with the registry's write token, so the workflow never runs anything from a pull request. It checks out the base branch, copies its scripts aside first, fetches the pull request's commits only as data for `git show`/`git diff`/`jq`, and passes every value through `env` rather than interpolating it into the script.
- A merge made with a workflow's token doesn't trigger other workflows, so the publish workflow regenerates the index itself; `regenerate-index.yml` still covers merges a maintainer makes by hand. Both go through `push-index.sh`, which retries when they race.
- `trunk add-owner`/`remove-owner`/`deprecate` still only talk to a registry server. On the public registry, co-owners are added with a pull request editing OWNERS, which a maintainer reviews.
- The workflow YAML hasn't run on GitHub Actions yet. Its scripts are tested locally (`test-validate-pr.sh`, `test-publish-policy.sh`), and its script block was run end to end against a local git origin with a stand-in for `gh`; the first real publish is the remaining check.

## Amendment (2026-11-13): no human in the loop

A one-time maintainer review doesn't match CocoaPods, where `pod trunk push` decides on its own, instantly. Every case that waited for a person is now decided automatically, as published or rejected:

- **A name that's already on CocoaPods trunk** can only be published here by one of its owners there, CocoaPods' own rule. `verify-trunk-owner.sh` decides from trunk's records, never from anything in the pull request. Trunk's API lists the pod's owners by email, and its latest podspec names the pod's repository and homepage. The publisher qualifies if their GitHub profile's public email is an owner's (GitHub only lets a verified address be public), or if GitHub credits their account with commits to the pod's repository made with an owner's email. GitHub only credits an account with commits whose email belongs to it, so this works with a hidden email too, and it's what matches most authors with no setup: checked against live data, it accepts `onevcat` for Kingfisher and Jon Shier for Alamofire, and rejects anyone else. For owners whose trunk email isn't linked to their GitHub account, controlling what the owners published also counts: the repository's GitHub account, public membership of the organization that owns it, a `.zorvok-owners` file in it, or `/.well-known/zorvok-owners` on the homepage's site (for binary-only pods). If nothing matches, the rejection lists exactly which of these would work for that pod.
- **OWNERS edits** are published when a current owner makes them and at least one owner remains — `pod trunk add-owner`/`remove-owner`, as a pull request. Anything else, an OWNERS file without a version, or a change outside `Specs/`, is rejected.
- **`prepare_command`** is rejected, as CocoaPods trunk does.
- **Infrastructure failures** don't wait for a person either. If the index can't be pushed after a merge, the workflow starts `regenerate-index.yml` itself (a `workflow_dispatch` from its token does start a run). If the check fails unexpectedly, the verdict is a rejection that says to run `trunk push` again.

A rejected pull request is closed, since no one would review it; the next `trunk push` opens a fresh one. `trunk push` (v0.1.2) needed no change: it already reported published and rejected verdicts, and simply never sees `needs-review` any more.

## Amendment 2 (2026-11-13): security review

A security review ([SECURITY-REVIEW.md](../../SECURITY-REVIEW.md)) found ways around the rules above, and a second review of the fixes found more. The publish path changed in these ways:

- **Judged on the registry's current tip, published as the workflow's own commit.** The workflow used to check a pull request against the commit it was based on, which its author chooses: an owner removed from `OWNERS` could still publish from a branch made before the removal. It now merges the pull request onto main's current tip itself (`git merge-tree`, without touching the working tree), commits the resulting files with the tip as the only parent, checks that commit against the tip, and publishes it with a plain `git push`, which only succeeds as a fast-forward. If main moved in the meantime, the push fails and the checks run again on the new tip, up to five times. None of the pull request's own commits enter the registry, so nothing hidden in its history (files it added and later removed, forged authors) does either. The pull request is then closed, published or not; `trunk push` trusts only the workflow's verdict comment, never GitHub's "merged" flag.
- **Owners are GitHub user IDs.** An `OWNERS` line is `<numeric GitHub user ID> <username>`, and only the ID counts: a username can be renamed and then registered by someone else, an ID never changes and is never reused. The workflow takes the author's ID from the event (`github.event.pull_request.user.id`), and `trunk push` writes the line (v0.1.4). Only the author may update their pull request: a push or reopen by anyone else (`github.event.sender.id`) is rejected, since it would be judged as the author's.
- **Trunk ownership is proven by email only, as on trunk.** The first amendment's repository-based proofs are gone. Owning the pod's repository, a `.zorvok-owners` file in it, public membership of its organization and `/.well-known/zorvok-owners` on its homepage could all be passed by someone else: GitHub doesn't record who held a username before, so after an owner renames or deletes their account, an old account and repository can be renamed into the freed names, and creation dates can't tell them apart; a homepage's domain can lapse. What remains is what GitHub has verified: the publisher's public email is a trunk owner's, or GitHub credits their account with commits to the pod's repository made with a trunk owner's email. "The pod's repository" is the one named by the version trunk published most recently, by trunk's own timestamps (a version sort would rank an old `2.0.0-beta.1` above `2.0.0`). A case variant of a trunk name (`alamofire`) is refused, checked against trunk's full `all_pods.txt`, and a list much shorter than trunk's 100,000-plus pods counts as trunk being unreachable rather than as the name being free.
- **Narrower pull requests.** Only pull requests into `main`; one pod per pull request; plain files only (mode 100644: no symlinks, submodules or executables); every podspec exactly one JSON object (jq reads a stream, so a second document could otherwise hide `prepare_command` from the check); renames count as a delete plus an add, so they can't move a published version; no new pod whose name differs from an existing one only in case; names and versions limited to a safe character set.
- **Text from a pull request is treated as untrusted everywhere.** The verdict comment quotes the reasons as an indented code block with control characters, carriage returns included, removed, so nothing renders as a link or a mention, and the CLI strips control and bidirectional-text characters from anything a server sends before printing it (`internal/safehttp`). `git clone` is no longer used at all; curl fetches are restricted to https (`--proto`, `--proto-redir`), with a time and size limit.
- **Tokens stay encrypted.** The CLI refuses an `http` registry or GitHub API URL unless it's this machine, and refuses to follow a redirect off https, since Go resends `Authorization` on a same-host redirect even to plain http.

The workflows also give each job only the permissions it uses, with none at the workflow level, and pin `actions/checkout` to a commit, which Dependabot keeps current. `scripts/test-publish-workflow.sh` runs the workflow's own script on simulated pull requests against live trunk data, including the removed-owner, hidden-history and other-pusher attacks.
