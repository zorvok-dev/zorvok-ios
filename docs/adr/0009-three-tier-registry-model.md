# ADR 0009: three-tier registry model, and splitting the repository

## Status
Accepted

## Context
Through Milestones 3-4 we built `registry-server`: a live Go HTTP API (accounts, sessions, package/version store) that someone has to run and pay to host. Through Milestones 5-8 we built federation (`zorvok install --native [--source <url>] | registry_url auto-federation`) so `zorvok install` can resolve dependencies from *any* configured registry URL, not just Zorvok's own.

Explicit product direction: Zorvok's own official public registry should not require the project to run and pay for a live server — it should deploy the same way the CLI does (`brew install zorvok`, free), using GitHub's own free hosting primitives (git, GitHub Pages) instead. At the same time, `registry-server` isn't wasted work: federation already treats "a registry" as nothing more than a URL a client resolves against, and `registry-server` is a legitimate thing for someone else to self-host.

This is directly analogous to how Maven works: Maven Central (the free, publicly hosted default) coexists with self-hosted Nexus/Artifactory instances organizations run themselves, and a project's `pom.xml`/build config just lists repository URLs — the build tool doesn't care which kind of server (or non-server) answers at that URL.

## Decision
Three registry tiers, all reachable through the exact same federation mechanism (ADR 0005-0008) — `zorvok install --native` with a configured source URL, no new CLI mechanism needed for any of them:

1. **CocoaPods' own registry** (`cdn.cocoapods.org`) — unchanged, already supported since Milestone 2/6.
2. **Zorvok's official public registry** — a static git repo (`zorvok-dev/zorvok-specs`), served via GitHub Pages (or even just `raw.githubusercontent.com`/a plain git clone — GitHub Pages is a nice-to-have CDN layer, not a hard requirement of the format). Implements the *exact same* CDN protocol `registry-server/cdn` already generates on the fly (ADR 0006: `CocoaPods-version.yml`, `all_pods.txt`, `all_pods_versions.txt`, `Specs/<name>/<version>/<name>.podspec.json`) — just as pre-committed files instead of live HTTP responses. Free to host; GitHub pays for the bandwidth, not Zorvok.
3. **Self-hosted enterprise/private registries** — `registry-server`, exactly as built in Milestones 3-4, unchanged. An organization runs it themselves (their own infrastructure, their own cost), configures `registry_url` to point at it, and gets everything Milestones 3-8 already built: accounts, ownership, immutability, rate limiting, the live CDN facade. Zorvok never hosts this on anyone's behalf.

`registry-server` is **not deprecated** — ownership of "run it yourself" moves from Zorvok to whoever needs a private registry, which was always its natural audience once federation existed. Nothing about its own architecture changes.

### What's genuinely new: ownership/immutability without a server
Tier 2 (the static public registry) has no database, no session tokens, no live validation — so Milestone 3/4's protections (first-publisher-wins ownership, reject-duplicate-version immutability, structural podspec validation) need a GitHub-native equivalent:

- **Publishing = a pull request** against `zorvok-dev/zorvok-specs`, not an API call. A GitHub Action runs on every PR and enforces, mechanically, before merge:
  - **Immutability**: the PR may only *add* files under `Specs/<name>/<version>/`, never modify or delete an existing version's files.
  - **Structural validation**: each added podspec must be valid JSON, and its `name`/`version` fields must match the path it was added at — the same check `registry-server/api`'s `validatePodspec` already does, reimplemented as a CI check since there's no server to run it.
  - **Ownership**: a `Specs/<name>/OWNERS` file (one GitHub username/email per line) is created by whoever's PR first adds that pod's directory, and subsequent PRs adding a new version under an existing pod name must be authored (or approved) by a listed owner. First-publisher-wins, same rule as `registry-server/packages`, enforced by the Action instead of a database constraint.
  - **No code execution**: the Action only ever reads/diffs file contents — it never evaluates a podspec as Ruby or runs anything from a submitted package, same rule as the server-side registry (brief §9).
- Index files (`all_pods.txt`, `all_pods_versions.txt`) are regenerated by the same Action from the resulting `Specs/` tree on every merge to the default branch, so they never drift from the actual podspec files — this is the static-CDN equivalent of `registry-server/cdn` computing them from the live store on every request.

### Repository split
Following from this, the single `zorvok` repo splits into three, matching the three concerns above that now have genuinely different deployment stories:

- **`zorvok-dev/zorvok-ios`**: the CLI — `cmd/zorvok`, `internal/*`, `engines/*`, `tests/fixtures`, and this project's architecture docs (ARCHITECTURE.md, ROADMAP.md, `docs/adr/`), since the CLI is what all three tiers exist to serve.
- **`zorvok-dev/zorvok-registry-ios`**: the self-hostable server — `cmd/zorvok-registry`, `registry-server/*`, unchanged. Tier 3's implementation.
- **`zorvok-dev/zorvok-specs`**: the static public registry — Tier 2. A new repo; its content is generated/validated, not hand-written.

These only ever communicated over HTTP (`internal/registry.Client`) in production, so splitting them doesn't change runtime behavior. It does break the integration tests that currently import `registry-server`'s Go packages directly to spin up an in-process `httptest` server (`internal/publisher`, `internal/registry`'s own tests) — those switch to running a real `zorvok-registry` binary as a subprocess, the same pattern already used for testing against real `pod` (skip, don't fail, if the binary isn't available).

## Consequences
- `registry-server`'s own tests, design, and all of ADR 0001-0008 remain entirely valid — nothing there changes. This ADR is additive (a new deployment tier) plus a repository reorganization, not a correction of prior work.
- The GitHub Action enforcing ownership/immutability for `zorvok-dev/zorvok-specs` is new, unreviewed surface — it is the thing standing in for `registry-server/packages`'s database constraints and auth checks, so it deserves the same scrutiny those got (tests, not just a YAML file hand-written and trusted). Scoped as its own follow-up given the size of this change already.
- `zorvok trunk push` doesn't yet know how to publish to a git-based registry (only the live HTTP API, Milestone 4) — adding that (clone-or-pull the specs repo, write the file, open/push a PR) is tracked as explicit follow-up work, not done in this change.
- Three repos means three places `go.mod`/CI/release tooling need to exist independently once Milestone 7 (public launch) is reached — accepted complexity, matching the Maven-like split this ADR is modeling.
